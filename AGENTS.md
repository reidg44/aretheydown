# AGENTS.md

## Purpose

Rust TUI that polls public status APIs (GitHub, AWS, Azure, Cloudflare, Google Cloud, OpenAI, Anthropic, Microsoft 365, and more) and shows each platform's current health on one screen. The owner uses it at the start of troubleshooting to rule out upstream outages before debugging their own infrastructure. `--serve` also serves a web page (`src/html.rs`), so keep fetching/parsing separate from rendering.

## Commands

- `just build` / `just run` / `just test`. Plain `just run` opens the TUI (`q` or Ctrl-C quits).
- `just run --once`: fetch every platform once, print text, exit. Add `--json` for JSON. Exit code 0 = all Operational, 1 = any Degraded/Outage/Unknown, 2 = could not run, usage or setup error.
- `just run --serve`: poll every platform on start and every 60s, serve the latest result as a web page at `http://127.0.0.1:7341/` and as JSON at `/api/status` (`--port`, `--bind`; both need `--serve`, which conflicts with `--once`/`--json`), and append each platform's status changes to the history file (`--history <path>`, default `$XDG_STATE_HOME/aretheydown/history.jsonl`, else `~/.local/state/aretheydown/history.jsonl`; records older than 30 days dropped at start). At start, after that prune and before the first poll is recorded, it backfills the history from the vendors' incident feeds (Statuspage and Google Cloud `incidents.json` only, `backfilled: true` records, only before each platform's earliest record and within 30 days; coverage can be shorter, since a Statuspage `incidents.json` holds only recent incidents; a failed feed is a warning naming the platform). With `[alerts] webhook` in the config (one URL or a list), it also POSTs a JSON alert to each webhook when a platform's level changes and holds for two polls; `[alerts] levels` (e.g. `["outage"]`) keeps only changes into or out of a listed level (docs/alerts.md has the payload). Ctrl-C or SIGTERM exits 0 (`serve::shutdown_signal`; SIGTERM is Unix only); a port that can't be bound exits 2. `brew services start aretheydown` runs it in the background through the tap formula's `service` block (`--serve` with default paths, `keep_alive`, log at `$(brew --prefix)/var/log/aretheydown.log`; docs/serve.md → Run in the background).
- `just run --at <time>`: print what each platform looked like at `<time>` (RFC 3339, `now`, `2h ago`/`1d 4h ago`, or local `HH:MM` (most recent past one), `today HH:MM`, `yesterday HH:MM`, `YYYY-MM-DD HH:MM`; a ` UTC`/`Z` suffix reads a clock form in UTC) from that history, `--once`-style text under an `At … (local), from history recorded by --serve:` line (a platform from a backfilled record has `(from vendor history)` after its description), or `--json` (`"backfilled": true` on those). Reads no config and fetches nothing. Exit codes as `--once`; 2 also for a bad time, an unreadable history file, or no record by then. Conflicts with `--serve`/`--once`. `--history` also works with the plain TUI run (its `History (last 7 days)` section reads the file); it is rejected with `--once`.
- `just lint`: `cargo fmt --check` + `cargo clippy --all-targets -- -D warnings`
- `just check`: lint + test. Run before every commit.
- CI (`.github/workflows/ci.yml`, on PRs and pushes to `main`): `check` runs `just check` on stable Rust, `msrv` builds on 1.88, `hooks` runs prek with `--skip cargo-fmt --skip cargo-clippy` (its betterleaks hook only checks staged changes, so it scans nothing in CI), `secrets` runs a pinned betterleaks release over the PR's commits (base..head) or, on pushes to `main`, the full history. When bumping the betterleaks hook's `rev`, bump `BETTERLEAKS_VERSION` and `BETTERLEAKS_SHA256` (the `linux_x64` line of the release's `checksums.txt`) in `ci.yml` too; the job fails if the versions differ. Not a required check. Actions are pinned to commit SHAs.
- Git hooks: prek + betterleaks (`prek install -f`, `prek run --all-files`). `betterleaks` is not on PATH; to scan a new fixture, `git add` it and run `prek run`.
- Release: users install with `brew install reidg44/tap/aretheydown`; the formula lives in the public repo `reidg44/homebrew-tap` (`Formula/aretheydown.rb`) and builds from this repo's git URL at a tag + revision. To ship a version: bump `Cargo.toml`, push a `vX.Y.Z` tag, then update `tag:`/`revision:` in the formula (docs/development.md has the steps).

## Conventions

- Rust edition 2024. Clippy `pedantic` is on (warn), and `just lint` treats warnings as errors.
- `unsafe_code` is forbidden.
- `Cargo.lock` is committed (this is a binary).
- Secrets go in `.env` (git-ignored); placeholder names live in `.env.example`.
- User docs: `README.md` is a short overview (install, main commands, a screenshot at `docs/images/tui.png`); the details live in `docs/*.md` (`screen`, `output`, `serve`, `history`, `alerts`, `probes`, `config`, `development`). Put new detail in the matching docs page, not the README. README and docs examples use the installed `aretheydown` command; only `docs/development.md` uses `just`.
- Port **7341** is the `--serve` web page and API's default (avoid framework defaults like 3000/5173/8000).

## Code layout

- `src/model.rs`: the shared model (`PlatformStatus`, `Level`, `Incident`; `PastIncident`, an `Incident` plus the `Level` it gave, for history backfill). An `Incident` carries an optional `stage` (the vendor's own word, no shared enum; `model::non_blank` trims and drops blanks) and `latest_update: Option<Update>` (`text`, `posted_at`; `Update::new` drops control characters, keeping newlines, trims, and gives `None` for blank text; `Update::latest` picks the newest, the first on a tie, so providers pass updates newest first). `PlatformStatus.probe: Option<Probe>` (`url`, `ok`, `code`, `elapsed_ms`, `description`) is what the platform's vendor probe saw this fetch; `skip_serializing_if` keeps it out of history lines, and `render::json` adds `"probe": null` itself (so `--at --json` has `"probe": null` on every platform). It never affects the level, sort, verdict, exit code, history, or alerts. `PlatformStatus.regions` (AWS only, `#[serde(skip)]`, so never in `--json` or history) lists the region code of every active event, counted by `[aws] regions` or not, for the TUI's region picker. `PlatformStatus.resolved` lists incidents that ended within `model::RESOLVED_WINDOW` (24h) of `fetched_at` (`model::resolved_recently`), newest end first, each with `ended_at` set (`None` on active incidents); it never affects the level, sort, verdict, or exit code. Every provider produces it; every UI consumes it. Combine levels with `Level::worst` (Outage > Unknown > Degraded > Operational). `model::worst_first` (built on `sort_worst_first`, which the TUI list also uses) sorts statuses that way (ties keep config order) and `model::verdict` builds the one-line answer (`All 5 operational` / `2 of 5 need attention: Cloudflare, AWS`; Unknown counts as needing attention); the TUI header and `--once` text both use them. `model::age(started_at, now)` formats an incident's age (`2h 14m ago`, `just now` for a future start; `model::elapsed` is the same without `ago`, `<1m` for a future start) and `age_seconds` gives whole seconds, never negative.
- `src/providers/`: one module per feed format (`statuspage.rs`, `aws.rs`, `azure.rs`, `gcp.rs`, `m365.rs`), plus `probe.rs` for vendor probes (`probe::DEFAULTS`, the 8 built-ins' URL + `probe::Expect` (`Code(401)` or `Class(4)` = `4xx`); `probe::result(url, check::Outcome, expect)` is the pure decision; `probe::run(client, target)` GETs on the client it is given (`fetch` passes `probe::client()`, a `OnceLock` around `alerts::client()`, which follows no redirects; tests pass their own), within `probe::TIMEOUT` = `check::TIMEOUT`; `check::get` is the GET both share), and `check.rs` for `[[check]]` (no feed: `Source::Check`, which `fetch_feed` hands to `check::run`; the pure `check::status(name, Outcome, expect, fetched_at)` decides level and description; its own `check::TIMEOUT` of 9s stays under the 10s platform timeout so a slow endpoint is Outage, not Unknown; `status_page` is the checked URL; `check::without_latency` keeps `history::changed` from re-recording a check whenever only its response time moved). `providers::builtin()` lists the default platforms, each with `Platform.probe` from `probe::default_for` (`Platform::new`, `statuspage`, and `check` give none). `providers::fetch` runs `fetch_feed` and, when the platform has a probe, `probe::run` together through `providers::with_probe` (`tokio::join!`; a failed feed becomes `PlatformStatus::unknown` there, so it keeps the probe and `fetch` returns `Ok`). `fetch_feed` does the HTTP GET for every source and hands the body to that module's pure `parse(name, body, fetched_at)`, so a new provider only writes `parse` and tests need no network. Three exceptions (the third, checks, is above): `fetch_feed` calls `aws::parse_in_regions` with the `[aws] regions` from config (`aws::is_region_code` validates codes; `aws::REGIONS` is the picker's built-in code/name list, from botocore's `endpoints.json` without the China and ISO partitions), and, for Statuspage, `fetch_feed` also GETs `<page root>/api/v2/incidents.json` alongside the summary (`providers::statuspage_incidents_url`, its own `RESOLVED_TIMEOUT` of 8s, under the 10s platform timeout) and hands both bodies to `statuspage::parse_with_resolved` with the platform's `[components]` list; a failed or unparseable `incidents.json` leaves an empty `resolved` and the summary's status untouched. `statuspage::parse_resolved` is the pure resolved-only parser (`parse`/`parse_watching` are the summary alone). History backfill: `providers::fetch_past(client, platform)` (`None` for sources with no incident history; `BACKFILL_TIMEOUT`, 10s, per request) GETs Statuspage `incidents.json` (plus the summary, for group names, only with `[components]`) or Google Cloud's `incidents.json` and hands them to the pure `statuspage::parse_past(incidents, summary, watch)` / `gcp::parse_past(body)`, every incident as a `model::PastIncident` (the `Incident` plus its `impact`/`severity` level); `statuspage::parse_resolved` and `parse_past` share `listed_incidents` (parse, link, `[components]` filter).
- `src/config.rs`: the optional TOML config (`[[statuspage]]` vendors, `[[check]]` endpoints (`name`, `url`, optional `expect` 100–599; appended after the vendors; names share one case-insensitive namespace via `config::new_name`), `hide` built-ins, `[aws] regions`, `[components]`: platform name → watched component/group names, applied with `Platform::watch_components` to any Statuspage platform; a key naming no platform, a hidden one, or a non-Statuspage one is an error; `[probes]`: platform name → `false` or `{ url, expect }` (`config::ProbeEntry` (`Toggle(bool)` or `Set`), untagged, its own `expecting` message), applied by `set_probe`: a url without expect expects 2xx, expect alone keeps the built-in url, a vendor without a probe needs a url; keys are found by `configured_platform` like `[components]`' (unknown/hidden is an error), a `[[check]]` key is an error, and no error repeats the url or a string expect; `[alerts]`: `webhook`, `--serve`'s alert URL or a non-empty list of them (`config::WebhookUrls`, untagged), and optional `levels` (non-empty, `--json` spelling, any case), validated by `config::alerts` into a `config::Alerts` (`webhooks`: duplicates dropped, each a `config::Webhook` whose `Debug` hides the URL and whose `position()` is its 1-based place in the list; `levels: Option<Vec<Level>>`); an unknown level is named in the error only when it is word-like (letters, digits, space, `-`, `_`, up to 20), so a pasted URL is never echoed). `config::load(--config path)` returns a `Loaded` (`platforms`, `alerts`); the TUI, `--once`, and `--serve` validate `[alerts]` (`--at` reads no config); only `--serve` uses it. `parse`/`apply`/`alerts` are pure. Webhook URLs are secrets: no config error repeats one, so `parse` reports TOML errors as `line L, column C: <message>` without toml's echo of the line, and hides every quoted value and any `://` word in the message (`config::http_url` checks both `[[statuspage]] url` and each webhook, its problem text never holding the URL). Example at `config.example.toml`. The TUI's region picker writes the file through `config::save_aws_regions(path, codes)`: it rereads the file, hands the text to the pure `with_aws_regions(text, codes)` (finds `regions` with `toml_edit::Document` spans and splices only those bytes, so every other byte stays; handles `[aws]`, dotted `aws.regions`, and inline `aws = {…}`; with none, appends `[aws]`; an empty list removes the `regions` line and an emptied `[aws]` header; the result must pass `parse`/`apply`/`alerts` and set exactly `codes`, errors through `redact_values`), skips the write when nothing changes (`Saved::Unchanged`; an empty pick with no file creates none), and writes `<file>.tmp` (mode 0600, then the old file's mode) renamed over the symlink's target.
- `src/fetch.rs`: `fetch_all` runs each platform in its own tokio task with a per-platform timeout (`DEFAULT_TIMEOUT`, 10s); a failure, timeout, or panic becomes `Level::Unknown` with `error` set (`fetch panicked: …`). It takes the fetcher as a closure so tests inject fakes; keep a fetcher's work inside the future it returns, or a panic escapes. `in_fetch_task()` says whether code runs inside one of those tasks.
- `src/render.rs`: text/JSON output (the web page is `src/html.rs`). Text starts with the verdict and lists platforms worst first, each followed by its `  probe: <description>, GET <url>` line (`render::probe_line`, shared with the TUI's `Probe:` line), with each incident's stage and update on one line cut by `render::shorten` to `UPDATE_TEXT_LIMIT` (200) characters plus `…`; JSON stays in config order, keeps the update text whole, and adds `age_seconds` to each incident and its `latest_update` (for `resolved` entries, measured from `ended_at`). A platform with resolved incidents ends with one text line, `2 resolved in the last 24h, latest: <title> (1h 5m ago)` (title cut like updates). The TUI detail pane shows the update text in full, line by line, under a `Latest update (stage, age):` heading. Both measure incident age against the platform's `fetched_at` (so `render` stays pure); the TUI measures against draw time (`view::draw(frame, app, now)`). The two differ on purpose. The exit-code policy lives in `src/main.rs`.
- `src/serve.rs`: `--serve`, the HTTP layer (axum, http1 only, on the main tokio runtime). `serve::poll(platforms, interval, tx, fetch, recorder, alerting)` fetches at once and then every `POLL_INTERVAL` (`fetch::REFRESH_INTERVAL`, 60s, shared with the TUI), publishing `Some(Arc<Vec<PlatformStatus>>)` on a `watch` channel, then hands the poll to a `history::Recorder` (a failed write is a stderr warning, polling goes on), then to the optional `serve::Alerting` (an `alerts::Alerter`, the `levels` filter, the webhooks' positions, and a sender closure `Fn(webhook index, payload)`; `serve::alerting(Option<config::Alerts>)` builds the real one, `None` without `[alerts]`; `serve::no_alerts()` is the typed `None` for tests), which sends each of that poll's alerts that `alerts::wanted` keeps to every webhook at once in one `JoinSet` and waits for them (each bounded by `alerts::TIMEOUT`, 10s), warning on stderr per failed send (`alerts::warning`: platform, `webhook N`, and error, never the URL; a panicked send prints a fixed line; dropped, not retried; the other webhooks still get theirs). `serve::alerting_line` is the start-up line (`sending level changes to 2 [alerts] webhooks (into or out of: outage)`); `serve::backfill(platforms, path, now, fetch_past)` runs once in the poller task before `poll` (the server answers 503 meanwhile): every platform's `fetch_past` spawned at once and awaited in order, then `history::read`, `history::backfill` per platform up to `history::earliest_for`, and one `append`; warnings for a failed or panicked feed (naming the platform) or file, never an error; returns the count. `serve::run` takes the whole `config::Loaded`; the fetcher, the recorder's writer, and the alert sender are injected closures like the TUI's, so tests count calls, writes, and POSTs with fakes. `serve::router(latest, status_pages)` only reads that channel (`status_pages` is `serve::status_pages(&platforms)`, name → `Source::status_page`, since `PlatformStatus` doesn't carry it): `GET /` → `200` `text/html; charset=utf-8` with `html::page`, or `503` with `html::loading_page` (reloads itself every 5s); `GET /api/status` → `200` with `render::json` (platform health never changes the HTTP status) or `503` `{"error": "first fetch still running"}`; `GET /healthz` → `ok`; axum gives `404`/`405` for the rest. Tests drive the router with `tower::ServiceExt::oneshot`, no socket. `serve::run` binds, warns on stderr for a non-loopback address (no auth), and stops on Ctrl-C. No stale-data keeping (that is TUI only).
- `src/alerts.rs`: `--serve` webhook alerts. Pure parts: `Alerter::observe(statuses) -> Vec<Alert>` (per platform a confirmed level plus a pending one with a count: a poll at the confirmed level clears pending, a different one starts or extends it, and the second poll in a row alerts `confirmed → pending`; a platform's first poll only seeds; alerts in `statuses` order), `wanted(&Alert, levels)` (the `[alerts] levels` filter: `from` or `to` listed, or no list; applied after `observe`, so a dropped change still moves the confirmed level), and `payload(&Alert)` (`text`, `platform`, `from`/`to` in `--json` spelling, `at` = the confirming `fetched_at`, `incidents` = active `title`/`url`; `text` cuts titles and errors with `render::shorten`). `post(client, webhook, payload)` sends it with `alerts::TIMEOUT` on `alerts::client()` (follows no redirects, so a redirect is reported as `HTTP 307 …` instead of a POST silently turned into a GET); its error is `HTTP <code>` or the error kind (`timed out after 10s`, `could not connect`, `the request failed`), never reqwest's message, which holds the URL. Without the `json` reqwest feature it sets `Content-Type` and the body itself.
- `src/html.rs`: the `--serve` web page, pure like `render` (ages against each platform's `fetched_at`). `html::page(statuses, status_pages)` is a whole document: verdict as `<h1>` and `<title>`, platforms worst first with the level spelled out (not color only), the probe line (`Probe: ` + `render::probe_line`, class `probe ok` or `probe failed`, text only, no link), error, active incidents (full latest update, `white-space: pre-wrap`), resolved list, status-page link, and the newest `fetched_at`. Inline CSS (light/dark via `prefers-color-scheme`) and a few lines of inline JS that re-fetch `/` every `fetch::REFRESH_INTERVAL` and swap `<main>`; no external resources. Every feed string goes through `escape`, and only `http(s)` URLs become links (`link`), so a feed cannot inject markup or a `javascript:` link.
- `src/history.rs`: `--serve` history and `--at`. The model types derive `Deserialize` too, so a line is a `history::Record` (`recorded_at`, `status`: the `PlatformStatus` itself, no `age_seconds`; `backfilled`, left out when false) in JSON Lines. Pure parts: `changed(last, statuses)` (a status is written when it has no earlier record or differs in anything but `fetched_at`/`resolved`/`probe`; `Recorder` also writes it with `probe: None`), `Recorder` (remembers what it wrote; a failed write is retried next poll), `parse` (skips unreadable lines, counts them), `at_records(records, t)` (latest record per platform at or before `t`, platforms in first-seen order), `earliest`/`earliest_for(records, name)`, `backfill(name, past, until, now)` (a platform's `model::PastIncident`s into `backfilled` records: one at each start or end where the level (worst active) or the set of active incidents changes, active incidents newest start first with no stage, update, or end; `Operational`/`No active incidents` once none is; only records `>= now - RETENTION` and `< until` (the platform's earliest record, else `now`), so a second run adds nothing; changes before the window still set the state the first one in it starts from; after `prune` drops a platform's oldest records, the next start may fill the freed span again, never among existing records), `timeline(records, name, now)` (the TUI's history section: one `history::Change` per change of `Level`, newest first, records keeping the level folded in, within `TIMELINE_WINDOW` (7 days) plus the change in force at the window's start, whose `from` is `None` like the oldest shown; records after `now` ignored), `retain` (`RETENTION`, 30 days; unreadable lines are kept, since they may come from another version), `parse_time` (the `--at` formats, case-insensitive: RFC 3339, `now`, `<n><m|h|d>… ago`, and clock forms in the zone of the `now` passed in, or in UTC with a ` UTC`/`Z` suffix; a bare `HH:MM` later than now is yesterday's; hand-parsed on chrono, no date-parsing crate), `default_path(var)`. File parts: `append` (creates the directory, one write per poll, starts with a newline when a cut-short write left the file without one; plain blocking `std::fs`, small enough to run on the poll task) `prune` (rewrite through `<file>.tmp`, run at `--serve` start), and `read` (`None` for a missing file; cut-short lines skipped). The `--at` runner (`run_at`, `records_at`) lives in `main.rs`; its output is `render::history_text`/`history_json`.
- `src/tui/`: the interactive UI. `tui::run(client, platforms, history)` is the entry point (`history`: the history file path, or why there is none); `app.rs` holds the pure, unit-tested state (selection, sort order, detail scroll, incident highlight, footer notice, refresh gating, key mapping); `App::key(KeyEvent)` is the loop's entry point (the open picker takes every key, else `Action::from_key` → `App::apply`), returning an `Effect` (`Refresh`, `Open(url)`, `Notice(text)`, or `SaveAwsRegions(codes)`) for the loop to carry out. `f` (`Action::Filter`) opens the selected platform's picker from its `app::Filter` (`AwsRegions(Option<Vec<String>>)`, set by `mod.rs`'s `filter_for`; `None` gives a `can't be filtered` notice): `picker.rs` is the pure checklist (`Picker`, `Item`, `Picker::key` → `picker::Outcome`; `/` filter typing, Space, Enter, Esc clears a filter then cancels), its items from `app::region_items` (`aws::REGIONS`, then config and `PlatformStatus.regions` codes not built in), drawn full screen by `view::draw_picker` with its own footer. Each row has a one-column probe mark between level and time (`view::probe_mark`: green `✓`, red `✗`, blank), and the detail pane a `Probe:` line under `Updated`; kept stale data takes the failed refresh's probe (`Entry::update`). Rows sort worst first by default (`s` toggles config order); `selected` is a row position, and `reorder` keeps it on the same platform when a refresh or the toggle moves rows (the first results instead select the top row, the worst platform). Stale data: when a platform's fetch fails (a status with `error` set) and its last good status is at most `app::STALE_LIMIT` (10 minutes) old, `finish_refresh` keeps that status and records an `app::Stale` (`error`, `failed_at`, read with `app.row_stale(row)`); past the limit, or with no good data, the Unknown status replaces it, and a good fetch clears the mark. The kept level drives the sort and the header verdict; the row shows a dim `stale 4m` (age since the last good fetch) in place of the clock, and the detail pane shows `Refresh failed at …: <error>` and `Showing data from 4m ago (shown as Unknown after 10m).` above the kept incidents (the fallback itself happens at the next refresh, so a tag can read `stale 11m`). TUI only: `--once` has no earlier data. `view.rs` draws it (tested with ratatui's `TestBackend`; the detail pane ends with `Resolved in the last 24h (N)`: title, components, `Resolved 2h 14m ago, lasted 39m`, and the URL as an OSC 8 link, re-filtered against draw time so kept stale data never shows one past 24h; Tab/`o` skip resolved incidents; after it, `History (last 7 days)` from `app.history()`, an `app::History` (`Missing`, `Unreadable(why)`, `Records`), built with `history::timeline` against draw time: `  Sat 02:14  Operational → Outage, lasted 39m`, incident titles joined with `; ` and cut by `render::shorten` on the next line, the date added past 6 days; nothing before the first read; `t` swaps the list and detail pane for the full-screen timeline (`app.timeline_open()`, its own scroll in `App::timeline` (`None` while closed), drawn by `view::draw_timeline`: every platform's `history::timeline` merged newest first, ties in config order (`app.names()`), under local-date headings `Mon 16 Nov`, `  07:15  <name padded>  from → to, lasted …`, the change count in the border; the same no-history message as the section); while it is open the arrow and page keys scroll it, `s`/Tab/`o` do nothing, and Esc (`Action::Back`, which quits from the list) and `t` close it, keeping the selection and detail scroll), `wrap.rs` word-wraps the detail pane's lines itself (hanging indent, exact line count), `link.rs` turns incident URL cells into OSC 8 hyperlinks after the pane is drawn (each cell a complete link with a shared `id`, kept one column wide by `CellDiffOption::ForcedWidth`; only printable-ASCII URLs up to 512 bytes, so feed text can't inject escapes), and `mod.rs` runs the loop: a `SaveAwsRegions` runs the injected `save` closure (`config::save_aws_regions` under `spawn_blocking` in `run`, which takes the `--config` path or `config::default_path()`) in its own task, one at a time; `apply_saved_regions` then sets the AWS platforms' regions and starts a refetch at once (aborting one in flight), or keeps the old ones, and `notify` puts the outcome in the footer for `NOTICE_DURATION`; quitting waits for a running save. Fetches go through `fetch::fetch_all_live` in a spawned task every 60s or on `r`, and each refresh also rereads the history file (`tui::run`'s `history` path, from `--history` or the default) through an injected `load_history` closure (`spawn_blocking`, never on the draw path; tests pass fakes); keys come from a std thread. `view::draw` returns the detail pane's `DetailViewport` (size, content length, the line each incident starts on), (the timeline's while it is open), which the loop hands to `app.set_viewport` so page keys know the page size, Tab can scroll the highlighted incident into view (`app.scroll_for`), and paging can move the highlight onto the screen. Tab/Shift-Tab move the highlight (it resets on a platform change and follows the same incident through a refresh); `o` opens its link, else the platform's status page (`Source::status_page`), through an opener closure injected into the loop like the fetcher (tests pass fakes). A failed open shows in the footer for `NOTICE_DURATION`. `run` wraps ratatui's panic hook so it skips the terminal restore for panics inside fetch tasks (`fetch::in_fetch_task`); otherwise a caught fetch panic would drop the screen out of raw mode. UI code only reads `PlatformStatus` and history `Record`s, and writes only the config's `[aws] regions`, through that `save` closure.
- `tests/fixtures/`: summaries captured from the live endpoints (Cloudflare's trimmed to ~25 KB: non-operational components and one upcoming maintenance kept, which must stay hidden; OpenAI's and Anthropic's are untrimmed captures of 2026-11-14, each with one live incident; `anthropic_incidents.json` is Anthropic's `incidents.json` of 2026-11-14 trimmed to its first five incidents (one unresolved, then resolved 2026-11-14 04:23, 2026-11-13 21:49, 15:38, 11:58); `m365_consumer.json` is an untrimmed capture of 2026-11-14 with nine `Operational` services and one `Service restored`). Recapture with `curl` when a format changes.
  Google Cloud's `incidents.json` (~290 KB live) is trimmed to a few incidents with `updates` and `service_key` dropped (betterleaks flags `service_key` as an API key) and `most_recent_update.text` cut short: `gcp_incidents_closed.json` holds four closed ones (one `high`); `gcp_incidents_active.json` is a real `high` incident with `end` removed plus two closed ones.

## Status sources (checked live 2026-11-13)

| Platform     | Endpoint                                            | Format |
| ------------ | --------------------------------------------------- | ------ |
| GitHub       | `https://www.githubstatus.com/api/v2/summary.json`  | Atlassian Statuspage JSON |
| Cloudflare   | `https://www.cloudflarestatus.com/api/v2/summary.json` | Atlassian Statuspage JSON |
| AWS          | `https://health.aws.amazon.com/public/currentevents` | JSON array of current events |
| Azure        | `https://azure.status.microsoft/en-us/status/feed/` | RSS (XML) |
| Google Cloud | `https://status.cloud.google.com/incidents.json`     | JSON incident list |
| OpenAI       | `https://status.openai.com/api/v2/summary.json`     | Statuspage-compatible JSON (checked 2026-11-14; no `scheduled_maintenances` key, incidents without `shortlink`) |
| Anthropic    | `https://status.claude.com/api/v2/summary.json`     | Atlassian Statuspage JSON (checked 2026-11-14; `status.anthropic.com` redirects here) |
| Microsoft 365 | `https://status.cloud.microsoft/api/posts/m365Consumer` | JSON array, one entry per consumer service (checked 2026-11-14; no sign-in; business tenant health needs Graph and is not read) |

Status pages that `o` opens: Statuspage vendors use the feed URL minus `/api/v2/summary.json`; AWS `https://health.aws.amazon.com/health/status`, Azure `https://azure.status.microsoft/en-us/status`, Google Cloud `https://status.cloud.google.com/`, Microsoft 365 `https://status.cloud.microsoft/`; a `[[check]]`, the URL it checks (the `--serve` page labels it `Status page` too).

Many other vendors also run Atlassian Statuspage (`/api/v2/summary.json`), so one Statuspage client covers a lot of platforms. Use `summary.json`, not `status.json`: only `summary.json` lists active incidents.

Statuspage resolved list: `incidents.json` (`{page, incidents}`, recent incidents newest first, 36–300 KB) entries whose `resolved_at` is within 24h of the fetch. Stage = `status` (`resolved`/`postmortem`); URL = `shortlink`, else `<page.url>/incidents/<id>` (OpenAI has no shortlinks). `[components]` applies with the active-incident rule; incident components carry `group_id` but no group rows, so group names match through the summary's components.

Statuspage `status.indicator` → `Level`: `none` → Operational, `minor` and `maintenance` → Degraded, `major`/`critical` → Outage, anything else → Unknown. In-progress maintenance (`scheduled_maintenances` with status `in_progress`/`verifying`) is listed with `IncidentKind::Maintenance` so a maintenance-Degraded platform always shows why; upcoming (`scheduled`) maintenance is skipped. Stage = the incident's `status` (`investigating`/`identified`/`monitoring`) or the maintenance's (`in_progress`/`verifying`); latest update = the `incident_updates` entry with the newest `created_at` (`body`), whatever the list order.

With a `[components]` list, the indicator is ignored. Names match (trimmed, case-insensitive) a component's or group's `name`; a group name covers every component whose `group_id` is that group's `id`; group rows themselves aren't counted. Components are taken from `components` plus any that only appear on an incident or in-progress maintenance (the Cloudflare fixture has no top-level `Workers`). Level = worst of: each watched component's `status` (`operational` → Operational; `degraded_performance`, `partial_outage`, `under_maintenance` → Degraded; `major_outage` → Outage; else Unknown), each counted incident's `impact` (`none` → Operational, `minor` → Degraded, `major`/`critical` → Outage, else Unknown), and Degraded per counted in-progress maintenance. An incident or maintenance counts when it lists no components or any of them matches. The description is `All N watched components operational` (`1 watched component operational`, `No watched components in the feed`) or `K of N watched components not operational: A, B, C and 2 more`, then `(M incidents on other components not shown)`, then `(not in feed: "X")`.

AWS event `status` (a string, e.g. `"3"`) → `Level`, using the codes from the Health Dashboard front end (`0` resolved, `1` informational/"Impacted", `2` degraded, `3` disrupted): `0` → Operational (resolved, not listed), `1` and `2` → Degraded, `3` → Outage, anything else → Unknown. An empty list is Operational; otherwise the platform takes the worst event (Outage, then Unknown, then Degraded). Each event becomes an incident titled `<region_name> (<region code from the ARN>): <summary>`, with `service_name` as its component, `date` as its start time, no stage, and as its latest update the `event_log` entry with the newest `timestamp` (epoch seconds, string or number; the log is oldest first): `message`. With `[aws] regions` set, only events whose ARN region code is in the list count; global events (no region code, or `global`) always count, and the description adds `(N in other regions not shown)`. Valid codes are a 2+ letter prefix, words, and a number (`us-east-1`, `us-gov-west-1`, `eusc-de-east-1`).

Azure RSS → `Level`: no `<item>` → Operational; any item → Degraded (the feed has no severity, so Azure never shows Outage). Each item becomes an incident with its title, `pubDate`, and link; no stage and no latest update (no feed sample with item text yet).

Google Cloud `incidents.json` → `Level`: the feed lists recent incidents, closed and open; only those without an `end` are active. Closed ones whose `end` is within 24h of the fetch go in `resolved` (same fields, `end` as `ended_at`). No active incidents → Operational; otherwise the worst active `severity` decides: `high` → Outage, anything else (`medium`, `low`, new values) → Degraded. Each active incident shows `external_desc` as its title, `affected_products[].title` as components, `begin` as start, `most_recent_update.text`/`.when` as the latest update (often a long markdown report, kept as-is), no stage (`most_recent_update.status` is product availability, e.g. `AVAILABLE`, not a stage), and links to `https://status.cloud.google.com/<uri>`.

Microsoft 365 `m365Consumer` → `Level`: each service's `Status` (trimmed, any case): `Operational`, `Available` → Operational (not listed); `Service restored` → listed but Operational (Microsoft leaves it up after a fix); `Service degradation` → Degraded; anything else (`Unknown`, new values) → Unknown. These are the values the page's own JS knows; the feed has no outage value, so Microsoft 365 never shows Outage. The platform takes the worst service; an empty array is Operational. Each listed service becomes an incident titled `<ServiceDisplayName>: <Title>` (the name alone when `Title` is blank), with the name as component, `AuthoredDateTime` as start (`0001-01-01` is Microsoft's "no time", read as none), `Status` as stage, `Message`/`LastUpdatedTime` as the latest update, and no URL. Description: `All N services operational`, `Operational (1 restored service still in feed)`, or `K of N services not operational: A, B (…restored…)`.

`[[check]]` (your own endpoint) → `Level`: a GET within 9s (`check::TIMEOUT`), redirects followed, body not read. The expected status (`expect`, else any 2xx) → Operational, `Responding: HTTP 200 in 142 ms`; any other status → Outage, `HTTP 503 (expected 2xx)`; no answer → Outage, `timed out after 9s`, `could not connect`, or `the request failed`. Never Unknown, never `error` (so the TUI's stale keeping never applies), no incidents. The URL is shown on screen and in `--json`: it must not hold a secret.

Vendor probes (`[probes]`, defaults in `probe::DEFAULTS`, all checked live 2026-11-16): GitHub `https://github.com/` 2xx, Cloudflare `https://www.cloudflare.com/cdn-cgi/trace` 2xx, AWS `https://s3.amazonaws.com/` 3xx (307), Azure `https://management.azure.com/` 4xx (400), Google Cloud `https://storage.googleapis.com/` 4xx (400), OpenAI and Anthropic `…/v1/models` 401, Microsoft 365 `https://outlook.office.com/` 3xx (301). Redirects are not followed, so a 3xx is judged as is. Results: `responding (HTTP 401 in 220 ms)`, `unexpected HTTP 503 (expected 4xx)`, `no answer (timed out after 9s | could not connect | the request failed)`. The `--serve` page shows a `Probe:` line under each description (failed ones in the warning color), and `/api/status` carries `probe` through `render::json`.

## Gotchas

- **AWS `currentevents` is UTF-16 with a BOM** (`content-type: application/json;charset=utf-16`). Decode it before handing it to a JSON parser, or parsing fails.
- AWS dates in that feed are Unix-epoch seconds as strings (e.g. `"1772369485"`).
- Azure only publishes an RSS feed; an empty feed means no active incidents.
- Azure's RSS dates end in a bare `Z` zone (`Fri, 13 Nov 2026 20:00:00 Z`); chrono's `parse_from_rfc2822` reads it as UTC, so no rewriting is needed.
- Rust here comes from Homebrew, not rustup: there is no `rustup` command and no `rust-toolchain.toml`. Minimum Rust is 1.88 (`rust-version` in Cargo.toml).
- The TUI footer's key help is wider than 110 columns: view tests that check the whole footer draw at 140 (`render_sized`).
- View tests: the `Started:` line is in local time, so its width (and whether it wraps) depends on the machine's time zone. Leave `started_at` out of tests that pin wrapped rows.
- chrono-tz is not a dependency, so `FixedOffset` has no daylight-saving gaps. To test a nonexistent local time, `history.rs` tests define `GapZone`, a `TimeZone` whose `offset_from_local_datetime` returns `LocalResult::None` for one hour.
- The live AWS feed sends `event_log[].timestamp` as a number, unlike `date` (a string); `as_integer` takes both.
- `tmux` is not installed. To check the TUI by hand, run the binary under a Python pty with a pyte screen (`uv run --with pyte python …`), send keys, and print `screen.display`. pyte drops OSC 8, so check links by searching the raw pty bytes for `\x1b]8;id=…;<url>\x1b\\`. Buffer cells holding links contain escape bytes; tests read them through `link::visible` / `link::target`. To confirm `o` opened the page, list Chrome's tabs: `osascript -e 'tell application "Google Chrome" to get URL of tabs of windows'`.
- `f` in the TUI writes the config file. Your own `~/.config/aretheydown/config.toml` may hold `[aws] regions`, so for a hand check run the TUI with `--config <tmp>` (and `--history <tmp>`), never the default path. With every platform but AWS and one Statuspage vendor hidden, the live AWS feed (two Middle East events on 2026-11-23) shows the description change after a save.
- To see a failing probe in the TUI, point one at a closed port: `[probes]\nGitHub = { url = "http://127.0.0.1:1" }` in a temporary `--config`; its row shows `✗` and it stays Operational.
- To make one platform fail on demand (stale data, errors), copy a Statuspage fixture to `<dir>/api/v2/summary.json`, serve it with `python3 -m http.server <port> --bind 127.0.0.1 --directory <dir>`, point a `[[statuspage]]` at `http://127.0.0.1:<port>` in a temporary `--config` (hide the built-ins), then stop the server and press `r`.
- `open::that_detached` (the `open` crate) still blocks on macOS: it waits for `/usr/bin/open`. The TUI runs it under `spawn_blocking`; keep it off the async threads.
- clap waives `requires = "serve"` on `--port`/`--bind` when an arg that conflicts with `--serve` (`--once`) is present, so they also carry `conflicts_with = "once"` (`--history` carries only `conflicts_with = "once"`: the TUI reads it too); they are `Option`s with defaults applied in `Cli::serve_addr`. `main.rs` tests pin every rejected combination.
- To check `--serve` by hand: `./target/debug/aretheydown --serve --port 0` prints the port it got; `curl` it; `kill -INT <pid>` and `kill -TERM <pid>` should exit 0 (`tests/serve_signal.rs` pins both on Unix). Open `/` in the built-in browser pane for the web page (check `prefers-color-scheme` both ways and phone width with `resize_window`). To see the 503 loading page, point a `[[statuspage]]` at the non-routable `http://10.255.255.1` (hide the built-ins): its first poll takes the full 10s timeout.
- To check history by hand: run `--serve --history <tmp>.jsonl` against the fake Statuspage server above, change `status.indicator` in its `summary.json`, wait two polls (~2 min, the interval is fixed at 60s), then `--at` a time on each side of the change, or open the TUI with `--history <tmp>.jsonl` (same `--config`) to see it in the `History (last 7 days)` section. Each restart re-records every platform.
- To check backfill by hand: `--serve --port 0 --history <empty tmp>.jsonl` with the built-ins prints `backfilled N history records from vendor incident feeds: …` within a few seconds (about 260 records on 2026-11-16); stop it, then `--at "1d ago" --history <same>` marks those platforms `(from vendor history)`. A second start prints no `backfilled` line and adds only the poll's records. The fake Statuspage server above has no `api/v2/incidents.json`, so each start warns `could not backfill history for <name>` (harmless; copy `anthropic_incidents.json` there to backfill from it).
- To check alerts by hand: run the history setup above with `[alerts] webhook = "http://127.0.0.1:<port>/hook"` and a small Python `BaseHTTPRequestHandler` with `do_POST` as the listener (`python3 -m http.server` answers POST with 501). Flip `status.indicator` to `major`: one POST about two polls later; back to `none`: the recovery POST; stop the fake server for one poll only: none. For several webhooks and `levels`, run two listeners on port 0 in one Python script (with the feed server in a thread too) and list both URLs; with `levels = ["outage"]`, `minor` sends nothing, then `major` and `none` send one POST to each.
- A config that hides every built-in and adds nothing is an error (exit 2). For a `--serve` that touches no network, hide them all and add one `[[statuspage]]` at a closed local port (`http://127.0.0.1:1`), as `tests/serve_signal.rs` does.
- Example or test Slack webhook URLs with 43+ characters after `hooks.slack.com/services/` match betterleaks' Slack webhook rule; keep placeholders short (`…/services/your/webhook/path`).
- betterleaks flags some public feed fields as secrets (Google Cloud's `service_key`). Strip such fields from fixtures rather than allowlisting.
